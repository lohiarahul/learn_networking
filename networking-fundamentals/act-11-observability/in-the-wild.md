# Act XI in the wild — the same mechanisms, industrialised

## The stack you will actually meet has a name for everything you just built by hand

Every production Kubernetes cluster you touch will already have some assembly of Prometheus, a log store, an alerting layer and (sometimes) a tracing backend — usually installed as `kube-prometheus-stack`, a Helm chart bundling Prometheus, Alertmanager, Grafana, a set of dashboards and the `ServiceMonitor` CRD that lesson 04 named but did not install. Nothing about what you have built so far is a toy version of this — it *is* this, minus the packaging. The log shipper you wrote by hand in lesson 02 is what Promtail or Fluent Bit are, restart-safe and configurable; Loki's own config file, hand-written in that same lesson, is the config file every real Loki deployment starts from; the RBAC token you minted for Prometheus in lesson 04 is what every `ServiceMonitor` needs behind the scenes; the `metric_relabel_configs` `labeldrop` you wrote in 04b is a config block that exists, verbatim, in every serious production Prometheus; the alert rule and Alertmanager route you wrote in lesson 05 are the exact shape a real `PrometheusRule` and `AlertmanagerConfig` compile down to; the dashboard JSON you provisioned by hand in 05b is the same JSON a `ConfigMap`-based Grafana dashboard provisioner reads in production. Reading a real cluster's `kube-prometheus-stack` values file after this act should feel like reading assembly instructions for parts you already recognise, not like meeting a new subject.

The honest reason this act declined that chart as an *entry point*: installing it first would have hidden every mechanism this act exists to teach, the same way installing `kubeadm` on day one of Act VI would have hidden the control plane. It earns its place here, at the end, as recognition rather than instruction — and it closes a real dangling thread. [Act VII 08c](../act-7-workloads/08c-when-the-chart-is-not-yours.md) had you read that exact chart's `charts/crds/crds/` subchart and count **ten CRD files you never opened**. This act opened exactly one of that family for real — `ServiceMonitor`, the schema Prometheus's own Operator watches to rewrite scrape configs, which lesson 04 named as "a CRD, nothing more" in Act VII 09's sense of the word. The other nine stay unopened here too, honestly: going further would mean installing the Operator this act deliberately declined, and the ten CRDs remain a good, concrete measure of how much of that packaging you have *not* yet been taught, rather than a number to feel bad about.

## The one number every SRE org tracks that you can already compute

`prometheus_tsdb_head_series`, which lesson 04b had you read directly, is the single most common cause of a real production Prometheus falling over — not disk, memory. Organisations running Prometheus at any scale set a **cardinality budget** per team or per metric, enforced at scrape time with exactly the `metric_relabel_configs` mechanism you used, and the postmortem for "why did our monitoring system stop answering queries" is overwhelmingly often "a label carrying something unbounded — a user ID, a URL, a Pod IP — and nobody noticed until the series count had already multiplied past what the box could hold." You have now seen the whole failure mode end to end, at a scale small enough to watch happen in thirty seconds instead of three weeks.

## `kubectl top`'s aggregation layer is not a curiosity

The APIService mechanism lesson 03 traced — the API server proxying `metrics.k8s.io` sideways to another Pod's cache rather than reading etcd — is the same mechanism behind every "custom metrics" or "external metrics" API a production cluster wires up for autoscaling on something other than CPU and memory (queue depth, request latency, a business metric). Every one of them registers as an `APIService` and every one of them has metrics-server's exact shape: a component polling on its own schedule, answering from memory, with no durability and no history. If a Horizontal Pod Autoscaler in a real cluster is scaling on a custom metric and the scaling looks "sticky" or delayed, the aggregation layer's caching behaviour — the same behaviour lesson 03 measured for `kubectl top` — is usually why.

## Loki, Alertmanager and Grafana, seen once each for the one thing they actually decide

None of the three earned a product tour in this act, and each one earned exactly the page the plan for this act promised: Loki (lesson 02) for indexing labels rather than lines, a decision that trades expensive full-text search for cheap ingestion and inverts the cardinality problem lesson 04b already priced; Alertmanager (lesson 05) for `group_by`, the label model's third appearance in this course, arriving unchanged to fix the exact same "too much undifferentiated noise" problem it fixed the first two times; Grafana (lesson 05b) for provisioning a dashboard from a JSON file and discovering that the file *is* the panel, with `step` as the one field that silently changes what question a chart is even answering. A production deployment of any of the three adds durability, multi-tenancy and a great deal of YAML on top of exactly these decisions — none of which changes what the decision itself was.

## eBPF observability, and the question lesson 06 answers directly

Act V and Act X already taught **Hubble**, Cilium's flow-observability layer — which watches every packet at the kernel level with zero application change, the eBPF-based category this act otherwise declines to install a second time. Pixie and similar tools extend the same idea to full request tracing without code instrumentation. Lesson 06 answers, directly and by measurement, the question this act asked you to hold onto the first time Hubble came up: an eBPF datapath sees a packet cross a socket boundary, going in and coming back out, and nothing about the CPU time a process spends *between* those two crossings. That gap — accurate at every boundary, silent about everything inside one process — is exactly why most organisations with a service mesh's automatic tracing still instrument their own code by hand: the mesh's spans are shaped like the gaps in your code, not like your code.

## Vendor SaaS platforms

Datadog, New Relic, Honeycomb and similar products are, underneath their dashboards, an agent (often a DaemonSet, sometimes an OpenTelemetry Collector) shipping the same metrics/logs/traces you have been reading raw in this act into somebody else's time-series database, at a price scaled to the volume you send. Nothing about the mechanism changes — the agent still scrapes, the cardinality still costs money exactly the way lesson 04b measured, the sampling still trades completeness against cost exactly the way lesson 06 measured — and the vendor's own pricing pages are frequently the most honest place to see the arithmetic of this act's own tables (a metric with high-cardinality labels is billed differently from one without, because the vendor is paying the same storage cost you would have; a trace ingested at 100% is billed differently from one sampled at 1%, for the same reason lesson 06 gave). Choosing one is a build-vs-buy decision about *ops burden*, not a decision about which mechanism is correct.

## Deliberately not covered here

**A Grafana dashboard-building tutorial.** A GUI walkthrough ages in months and teaches nothing transferable; lesson 05b built the same panel from its own `query_range` JSON first, which is the part that survives a UI redesign.

**Loki, Alertmanager and a tracing backend as a product tour.** Each earned exactly one page, for exactly one design decision, in lessons 02, 05 and 06 respectively — never a chart, never an operator, never a second container installed for redundancy or scale.

**The OpenTelemetry Collector's pipeline configuration.** OTLP's real contribution is being a wire format that ended an n×m adapter problem between every language and every vendor — lesson 06 gave it one paragraph, on purpose, and declined the YAML pipeline in front of it.

**An SRE-book chapter on error budgets as philosophy.** Lesson 05 gave the arithmetic instead — how a 14.4× burn rate consumes a 30-day error budget in about an hour — as one page of division, not a chapter of prose.

> **The question to carry out of this act:** every mechanism here is a decision about what to throw away, made before an incident by someone who did not know what the incident would be. What does your own cluster keep, and did anyone decide that on purpose?
