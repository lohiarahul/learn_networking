## Act 7 — workloads, scheduling, storage, config  ⟨complete: 10 lessons + all supporting pages⟩
Spine: **a Pod spec is a bundle of claims, and each claim is read by a different loop** (`requests`→scheduler · `limits`→kubelet→kernel/cgroup · probes→kubelet vs endpoint controller · `volumes`→kubelet/CSI · `replicas`→a controller). Pays off `act-4/01b-cgroups.md`'s "who reads that *second* number?" and `act-1/06b`'s "who decides where the surviving path points?" (which mis-promised Act V).
- `01-pod-to-deployment.md` — why three objects to run one program — bare Pod = **one machine's promise** (kubelet restarts the *container* via `restartPolicy`, proven with Act VI's `crictl stop`; lose the node and it is gone, and **`drain` refuses without `--force` because nothing owns it**); `ownerReference` Pod→RS→Deployment as the field a controller reads (and why deleting an owner collects dependents); a rolling update needs **two** ReplicaSets so a third object must conduct them — old RS kept at `DESIRED 0` with its template intact; `pod-template-hash` is what stops the two loops fighting over the same Pods; **none of the three picks a node** — they hand off through one empty `spec.nodeName`
- `02-rolling-updates.md` — the percentages you never typed — `maxSurge` 25% rounds **up** / `maxUnavailable` 25% rounds **down** (asymmetric on purpose: spend a Pod, not availability — so 3 replicas never dip below full capacity); **a rollback is not an undo log** — old ReplicaSets are kept at `0` with templates intact, so `rollout undo` is the same verb aimed at a shelf you kept → `revisionHistoryLimit` limits your ability to *roll back*, not disk; `CHANGE-CAUSE` is an annotation nothing writes (`--record` is gone); **two kinds of bad deploy** — a broken image is *safe* (availability never rises, old Pods serve, ends at `progressDeadlineSeconds` 600 → `ProgressDeadlineExceeded`) while a **false ready signal is dangerous** because the rollout *succeeds* at full speed and `maxUnavailable` is counting Pods the cluster believes are fine; `minReadySeconds: 0` = no probation
- `03-probes.md` — same syntax, two readers, opposite consequences — **readiness** fails → kubelet writes a Pod condition → the *endpoint controller* marks `ready=false` on the EndpointSlice (Act V) → traffic stops, while `STATUS` stays `Running` and `RESTARTS` stays `0`; **liveness** fails → the kubelet on that node *kills the container*, nobody else involved; toggled live by `exec: cat /tmp/ready` and `kubectl exec -- rm`; **the cascade**: a liveness probe that checks a *dependency* fails on every replica at once → service-wide `CrashLoopBackOff` from a 5-second blip → the test is **"if this check fails, would a restart fix it?"**; `startupProbe` suspends the other two while failing (replacing `initialDelaySeconds` as one number trading startup patience against detection speed); **`timeoutSeconds: 1` is the trap** — a slow probe counts as failed, so load causes restarts which cause load; detect time = `periodSeconds × failureThreshold` (~30s on defaults)
- `04-scheduling.md` — **pays off `act-4/01b-cgroups.md`'s dangling question** — `limits` are enforced by the *kernel, continuously, against reality*; `requests` by the *scheduler, once, against arithmetic* (a ledger, never actual usage) → **a cluster can be full and idle simultaneously**, the biggest source of over-provisioning; **QoS is derived, not written** (`Guaranteed`/`Burstable`/`BestEffort`) and sets eviction order, so "leave resources out" = invisible to the ledger *and* first to die; `nodeSelector` (exact, hard) → `nodeAffinity` required/preferred with `In`/`NotIn`/`Gt`/`Lt`, and **`IgnoredDuringExecution` because `spec.nodeName` is written once**; taints repel / tolerations only *permit* (never attract); `NoSchedule` vs `PreferNoSchedule` vs **`NoExecute`** (evicts) → every Pod silently carries `not-ready`/`unreachable` `NoExecute` tolerations at `tolerationSeconds: 300`, **which is the ~5 min before a lost node's Pods move**; `topologySpreadConstraints` `maxSkew`/`topologyKey` (hostname→nodes, zone→AZs) and `DoNotSchedule` vs `ScheduleAnyway` (the latter gives up exactly when you need it); **`FailedScheduling` is a per-node tally, distinct from Act VI's `Events: <none>`**
- `05-configuration.md` — one value, two consumption paths, different physics — **env is copied into process memory at `exec()` so the kernel offers no way to change it** (immutable for the process's life; changing it = a rollout; every *child process* inherits it) vs a **mounted ConfigMap/Secret volume = a directory, one file per key, rewritten by the kubelet on a ~1min poll via an atomic symlink swap** (`key -> ..data -> ..timestamp/`, the same magic-symlink trick Act I read in `/proc`) — watched live by a container printing `env=` and `file=` side by side; **`subPath` bypasses the swap and never updates** (silent, only bites in production); `immutable: true` stops the kubelet watching; **three plaintext locations for one Secret** — etcd (Act VI's `grep -a` on a snapshot), the node's `/var/lib/kubelet/pods/<uid>/volumes/kubernetes.io~secret/<vol>/<key>` (**tmpfs — RAM not disk**, but a node shell reads it with no credentials), and `/proc/<pid>/environ`; **a Secret is not encryption, it is a separate object with separate access control**
- `06-storage.md` — **pays off `act-1/06b`'s "who decides where the surviving path points?"** (which mis-promised Act V) — **"survives" is three different promises with identical-looking YAML**: `emptyDir` = a kubelet directory under `/var/lib/kubelet/pods/<uid>/`, survives a container restart only (new Pod = new UID = empty; cannot cross nodes; hence `drain --delete-emptydir-data`); a **PVC** is a separate object with its own lifetime → `StorageClass` → a PV a *provisioner* created, and it sits `Pending` until a Pod needs it because **`WaitForFirstConsumer` makes placement and storage one decision** (the volume *is* on a node); `local-path` pins the PV with `nodeAffinity` to one node → **cordon it and the Pod is `Pending` forever, lose it and the data is gone**; promise three needs storage on no node and **is the same manifest** — nothing in the Pod spec reveals which you got, only `kubectl get storageclass`; `accessModes` are a *request* (`ReadWriteOnce` = one **node**, so two Pods there can both write); **`allowVolumeExpansion: true` is a promise the provisioner must keep** — on `local-path` the API server accepts the resize and `status.capacity` never moves; `reclaimPolicy` `Delete` vs `Retain` (`Recycle` is *removed*, not deprecated)
- `07-the-other-workload-kinds.md` — **three assumptions each broken once** — Act V's hand-built `db-0`/`db-1`/`db-2` + headless Service *was* a StatefulSet, so the lesson asks what the controller adds: **ordered creation** (won't make `db-1` until `db-0` is Ready) and **`volumeClaimTemplates` → one PVC per replica** named `data-db-1`, *derivable from the Pod name* — which is the whole identity mechanism (identity is a string, as Act V found for DNS); **scaling down deletes Pods and KEEPS volumes** (the controller can't tell shrink from restart, so it makes the recoverable choice) and scaling back up rebinds the old disk; `serviceName` is the `subdomain` field set for you and must be headless. **DaemonSet has no `spec.replicas` at all** — the count is a *derived fact in `status.desiredNumberScheduled`*, an exception to the act's spine — and it auto-tolerates `node.kubernetes.io/unschedulable`, **which is why `drain` needs `--ignore-daemonsets`**: evicting one produces an identical Pod on the same node a second later (a toleration with **no key** + `Exists` is how anything reaches a control-plane node). **Job: `restartPolicy: Always` is rejected by validation** — derived, not memorised: `Always` restarts on *exit* including exit 0, and `Succeeded` requires staying exited, so the event that finishes the Job is the event that restarts it; `completions` vs `parallelism`; **failed Pods are kept because their logs are the evidence**; `backoffLimit` (failures, exponential) vs `activeDeadlineSeconds` (wall clock, overrides it); `ttlSecondsAfterFinished` is the only cleanup — and is why Act V's Gateway install needed `--ignore-not-found`. **CronJob's output is Job objects** (CronJob→Job→Pod, lesson 01's `ownerReference` chain again): `concurrencyPolicy: Allow` overlaps by default, the schedule is in the *controller's* timezone, and `startingDeadlineSeconds` means a CronJob can be silently not running on a healthy cluster
- `08-shipping-a-set-of-objects.md` — **neither Helm nor Kustomize is a Kubernetes feature** — `kubectl api-resources` has no `Chart`, `Release` or `Kustomization`: both are *client-side*, both POST the kinds that already exist, so nothing in the cluster can tell which tool made an object and `kubectl get -o yaml` is always the truth. Two opposed bets: **Kustomize says your YAML is real YAML and you describe a transformation** (built into kubectl; `kubectl kustomize` renders, `apply -k` sends; `namePrefix`/`namespace`/`images`/`replicas`/`patches`; an overlay points *at* a base that doesn't know it exists; `namePrefix` renames but does **not** touch labels, or the selector would stop matching) vs **Helm says your YAML is a program that prints YAML** (`templates/` do not parse as YAML at all; `helm template` before `helm install`, always). The payoff beat: **`configMapGenerator` puts a content hash in the name and rewrites the Deployment's reference**, so a config change *becomes* a rolling update — solving structurally what lesson 05 said you had to remember to do by hand. And the discovery: since the API server has no `Release` kind, **Helm's state lives in a Secret** — `sh.helm.release.v1.<name>.<rev>`, type `helm.sh/release.v1`, payload = the rendered manifest gzipped and base64'd *twice* — which is why `helm rollback` is a stored-manifest replay (contrast lesson 02: `kubectl rollout undo` scales an old ReplicaSet; **neither is an undo log**) and why `kubectl scale` behind Helm's back leaves `helm list` cheerfully reporting `deployed` until the next upgrade diffs. Derived trade-off: text templating can express `if` but cannot guarantee valid YAML; object transformation cannot produce invalid YAML but has no `if` (a condition is a *different overlay*). Deprecated-but-everywhere: `bases:`→`resources:`, `patchesStrategicMerge:`/`patchesJson6902:`→`patches:`
- `09-adding-a-kind.md` — **pays off Act V's unexplained CRD apply** (the eleven objects that survived cleanup) and resolves the apparent contradiction with lesson 08 — **a CRD extends the STORE, it does not add a LOOP**: you extend the API by POSTing an object *to* the API, the custom object lands at `/registry/<group>/<plural>/<ns>/<name>` in the same etcd filesystem as `apps` (Act VI), and then **nothing runs at all** — `replicas: 2` with no replicas of anything, which is the lesson. Free without code: REST endpoint, watch stream, uid/resourceVersion, `kubectl explain`, and **server-side** schema validation (`curl` is rejected too). **`status` as a separate subresource so permissions can differ** — a controller may write status and be forbidden spec (sets up Act X); **`scale` makes `kubectl scale` work on an invented kind** because the subresource is generic and you name the field; `additionalPrinterColumns` reveals that **kubectl has no knowledge of any kind** — every table ever read came from these. Then the reader **writes an operator in ~25 lines of shell** (watch/compare/act from Act VI), deletes its Deployment and watches the loop restore it: **an event handler must be right once, a loop only has to be right eventually**, which is why controllers re-derive rather than diff. ## Act 8 — trust on an untrusted wire (Stage 4, cryptography)  ⟨in progress: 1 lesson; no supporting files yet⟩
Spine: **cryptography is not one thing but four separate promises** — integrity (a hash) · authenticity with a shared secret (HMAC) · confidentiality (a cipher, then AEAD) · agreement between strangers in public (DH) · authenticity without a shared secret (signatures, certificates, a chain) — each mechanism keeping one promise and leaving a specific hole that motivates the next. Second spine: **nothing here is impossible, everything is merely infeasible, and infeasible is a number** — so the habit is arithmetic, not faith. Pays off Act III's explicitly-named TLS cliffhanger. **No cluster**: `openssl` on the reader's own machine.
- `01-hashing.md` — opens on a question with nothing to do with secrecy: **how do you check a large thing is unchanged without having the large thing?** — so the answer must be small, hence a fixed-width one-way function; **avalanche measured, not asserted** (one input bit flipped → **124 of 256** output bits change, and *half* is the interesting answer because half is what two *unrelated* random numbers give, so no trace of the input's structure survives to work backwards along); irreversibility derived **from the sizes** (2^8000000 inputs → 2^256 outputs, so the information is *destroyed*, not hidden — which reframes "we hash your passwords" as a claim about destruction, though guessing still works); the three resistance properties **derived from who the attacker is** rather than listed — 2nd-preimage (substitutes a download), preimage (has your password database), **collision (AUTHORS both documents, and is strictly the weakest)**; the birthday bound derived from pairs growing as the square → **collision resistance is half the output bits, always**, which is why 256-bit hashes are not paranoia; then **the reader breaks MD5 themselves** with the Wang–Yu 2004 blocks — two 128-byte files differing at byte 20, identical `79054025255fb1a26e4bc422aef54eb4`, different SHA-256 — and learns precisely what that costs: still fine for a corrupted mirror (no second preimage known), **useless the moment the file's author is the adversary**; plus **appending the same bytes to both preserves the collision** (verified: `a73aac8c…` for both), which is how a curiosity becomes a forged document. Closes on the length-extension trap: `SHA256(body + secret)` leaks a valid signature for an extended message without revealing the secret, because a hash was asked to keep the *wrong promise* — it has no notion of a sender
